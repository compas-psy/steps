# ADR-0001. Фиксация тулчейна: Node 24.20.0, pnpm 10.33, TypeScript ровно 5.9.3

- Статус: принято
- Дата: 2026-08-30
- Автор: владелец требований (через агента, пакет работ E00.1)
- Отклонение от: не отклонение, а конкретизация `docs/spec/SPEC/00_MASTER_IMPLEMENTATION_TZ.md`
  §2 («Node.js 24 LTS+», «pnpm 10+», «TypeScript 5.9+ strict») — ТЗ задаёт
  нижнюю границу диапазона, этот ADR фиксирует точные версии.

## Контекст

SPEC §2 требует «Node.js 24 LTS+», «pnpm 10+ workspaces», «TypeScript 5.9+
strict» — диапазоны, не точки. Диапазон без точки — это разное поведение CI
и локальной машины разработчика в зависимости от того, когда каждая из них
последний раз обновлялась; для монорепозитория на 11+ пакетах и трёх
нативных платформ (Android/Windows/Web) это источник «у меня работает».

На момент реализации пакета работ E00.1 в окружении уже установлены:
Node 22.22.2 (не подходит — ниже нижней границы SPEC), pnpm 10.33.0
(подходит), Rust 1.94.1, JDK 21.0.10. Требуемый Node доступен как готовый
тарболл v24.20.0 «Krypton» и смонтирован в `/opt/node24`, слинкован в
`/usr/local/bin/node`.

Отдельный вопрос — TypeScript. В npm-реестре на момент работы уже
опубликован TypeScript 7.0.2 — нативный порт компилятора (Corsa/Go),
объявленный как next-generation превью. SPEC говорит только «5.9+», что
формально разрешает и 7.x.

## Решение

Фиксируем точки, а не диапазоны:

| Инструмент | Версия                             | Где закреплено                                                        |
| ---------- | ---------------------------------- | --------------------------------------------------------------------- |
| Node.js    | **24.20.0**                        | `.nvmrc`, `package.json` → `engines.node: ">=24.20.0"`                |
| pnpm       | **10.33.0**                        | `package.json` → `packageManager: "pnpm@10.33.0"`                     |
| TypeScript | **ровно 5.9.3** (без `^`, без `~`) | `package.json` каждого пакета → `devDependencies.typescript: "5.9.3"` |

TypeScript пиним точным значением, а не диапазоном `^5.9.3`, по решению
владельца: **TypeScript 7.x, при всей доступности в реестре, брать
нельзя.** Причины:

1. Это переписанный с нуля нативный компилятор (Corsa) с иной кодовой
   базой, чем 5.x-линейка — не патч-релиз в привычном смысле semver, а
   новое поколение инструмента.
2. Экосистема плагинов и интеграций (typescript-eslint/oxlint-парсер,
   IDE-тулинг, `ts-node`-подобные раннеры, Vite/Vitest интеграция) на
   момент фиксации ещё не имеет зрелой поддержки 7.x — риск ломки
   тулчейна на 11+ пакетах ради версии, преимущества которой (скорость
   компиляции) для монорепозитория этого размера пока не критичны.
3. `^5.9.3` в `package.json` не защищает от 7.x: caret-диапазон `^5.9.3`
   ограничен мажором `5`, поэтому по факту уже исключает 7.x — но точная
   фиксация (без `^`) дополнительно исключает и любой промежуточный минор
   `5.10+/5.11+`, которого владелец не проверял. Разница между «не
   поднимется до 7.x» (уже верно для `^5.9.3`) и «не поднимется вообще
   без явного решения» (только у точной версии) — сознательный выбор в
   пользу второго: апгрейд тулчейна — это ADR, а не побочный эффект
   `pnpm install`.

Апгрейд TypeScript (5.10+, а тем более 7.x) — предмет отдельного ADR,
когда экосистема плагинов дозреет и апгрейд можно будет обосновать, а не
просто «потому что вышла новая версия».

## Последствия

**Плюсы**

- Воспроизводимая сборка: CI, контейнер разработки и любая будущая машина
  получают побитово одинаковый тулчейн, а не «5.9 или новее на момент
  установки».
- `pnpm install` не может тихо протащить TypeScript 7.x через транзитивный
  апгрейд диапазона — только явным ADR.

**Минусы и как они удерживаются под контролем**

- Точная фиксация версии означает, что патч-фиксы TypeScript 5.9.x (если
  выйдут) не подхватываются автоматически — команда должна сознательно
  поднять версию. Это плата за воспроизводимость; критичные фиксы
  компилятора для монорепозитория такого размера — редкость, а
  неожиданный дрейф поведения `strict`-режима на 11+ пакетах — не редкость.
- В контейнере `node` по умолчанию резолвится в Node 22.22.2, потому что
  `/opt/node22/bin` стоит в `PATH` раньше `/usr/local/bin` (куда
  слинкован Node 24). Это окружение, не решение ADR — работающие команды
  обязаны явно ставить `/usr/local/bin` впереди `PATH`
  (`export PATH="/usr/local/bin:$PATH"`) или вызывать бинарник напрямую;
  `node --version` без этой поправки лжёт об активной версии.

## Дополнение: oxlint и его JS-плагин пинятся точно

`oxlint` и `oxlint-plugin-eslint` зафиксированы точными версиями `1.80.0`,
без `^`, по той же логике, что и TypeScript, но по другой причине.

Правило адгезии дизайн-системы (запрет сырых hex, px и чужих `font-family`)
реализовано через `no-restricted-syntax`, которого у oxlint нет нативно: он
подключается механизмом JS Plugins, а тот сам объявлен как alpha. Версии
плагина и линтера обязаны совпадать.

Это **релизный гейт**: SPEC §16 требует, чтобы CI отклонял литералы вне
token layer. Гейт, который перестал ловить нарушения, хуже отсутствующего —
он создаёт ложную уверенность и молчит. Диапазон `^1.80.0` позволил бы
обновлению лок-файла подменить alpha-API под гейтом, и падения при этом не
случилось бы: линтер бы просто перестал понимать правило. Точная версия
делает такое обновление осознанным шагом с прогоном проверки на заведомо
нарушающем файле.
