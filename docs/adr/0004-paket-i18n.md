# ADR-0004. Отдельный пакет `packages/i18n` сверх дерева SPEC §3

- Статус: принято
- Дата: 2026-08-30
- Автор: владелец требований (через агента, пакет работ E00.1)
- Отклонение от: `docs/spec/SPEC/00_MASTER_IMPLEMENTATION_TZ.md` §3 — дерево
  монорепозитория там перечисляет 10 пакетов (`contracts`, `core`,
  `storage`, `sync`, `nlp`, `importer`, `ui`, `app`, `telemetry`,
  `platform`); `packages/i18n` в этом списке нет.

## Контекст

SPEC §13.1 («Localization contract») формулирует жёсткие требования:

- «Every user-facing string lives in i18n catalog; reusable components
  contain no literal product copy.»
- «Missing Russian key/fallback-to-key in production build is a CI
  failure.»
- «Architecture must allow future locales without forking components or
  domain behavior.»

Это требует физического места, где живёт каталог строк, и CI-шага, который
проверяет полноту `ru-RU`. SPEC не называет это место: §3 перечисляет
десять пакетов, ни один из которых не подписан явно как «сюда идут
строки». Ближайшие кандидаты и почему каждый не подходит:

- **`packages/ui`** — явно запрещено этим же ТЗ и решением ?13
  (`.ultraplan/open-questions.md`): "Generic-примитивы... по образцу...
  задачное... проектируем с нуля" — но нигде не сказано, что `ui` носит
  продуктовый копирайт. Наоборот, весь дух §3 («ui: tokens/components») —
  это переиспользуемые примитивы без бизнес-текста, чтобы дизайн-система
  была продуктово-нейтральной (её токены и так буквально заимствуются у
  ЗАПИСОК/СИМПАС — продуктовый текст туда просачиваться не должен).
- **`packages/app`** — здесь по SPEC §3 живут «ALL product screens/routes/
  behavior». Строки логически принадлежат экранам, но если положить сам
  каталог сюда, каждый импорт строки из `core`/`nlp`/`importer`
  (например, текст ошибки валидации из `@shagi/core`, см. таблицу
  ошибок §11 у ЗАПИСОК-аналога) потянет за собой весь `app` —
  циклическая или как минимум неестественная зависимость домена от
  экранного пакета.
- **`packages/contracts`** — это DTO/Zod-схемы формы данных, не текст для
  человека; смешивать их означало бы, что смена одной строки перевода
  требует пересобирать контракт данных.

## Решение

Добавляем `packages/i18n` в дерево монорепозитория как одиннадцатый
пакет, не предусмотренный SPEC §3, но не противоречащий ему: SPEC не
запрещает дополнительные пакеты, только фиксирует обязательные десять.

`packages/i18n` отвечает за:

- плоские JSON-каталоги строк по namespace (решение по вопросу ?12 в
  `.ultraplan/open-questions.md`);
- ICU MessageFormat для множественного числа (в русском три формы: 1,
  2–4, 5+ — простой `count === 1 ? ... : ...` их не покрывает);
- CI-проверку полноты `ru-RU` и запрет fallback-to-key в production-сборке
  (SPEC §13.1, дословное требование).

Импортируют `@shagi/i18n` те пакеты, которым нужен текст для
пользователя — в первую очередь `@shagi/app`, и по мере надобности
`@shagi/core`/`@shagi/nlp`/`@shagi/importer` для текстов ошибок и
подсказок, которые логически принадлежат домену, а не экрану. `@shagi/ui`
каталог **не импортирует** — это инвариант, а не рекомендация (см.
заголовочный комментарий `packages/ui/src/index.ts`).

## Последствия

**Плюсы**

- Единая точка, где физически проверяется полнота `ru-RU` — CI-гейт из
  §13.1 реализуется одним пакетом, а не размазывается по `app`/`core`/
  `nlp`/`importer` каждый со своим фрагментом каталога.
- `packages/ui` остаётся продуктово-нейтральным конструктивно: в нём
  физически неоткуда взять продуктовую строку, потому что каталог строк
  лежит не там и `ui` его не видит.
- Будущие локали (SPEC §13.1: «allow future locales without forking
  components or domain behavior») — это новый файл каталога в
  `packages/i18n`, а не архитектурное изменение.

**Минусы и как они удерживаются под контролем**

- Лишний пакет в графе зависимостей монорепозитория, которого нет в
  нормативном дереве SPEC §3 — риск, что читатель ТЗ ожидает ровно
  десять пакетов и не найдёт одиннадцатый. Удерживается этим ADR и
  README `packages/i18n`, которые явно ссылаются друг на друга.
- `@shagi/core`/`@shagi/nlp`/`@shagi/importer`, импортируя `@shagi/i18n`
  для текстов ошибок, получают зависимость домена от пакета со строками —
  сознательно принято как меньшее зло по сравнению с альтернативой
  (хардкод текста ошибки в домене в обход каталога, что прямо запрещено
  §13.1). Граница держится тем, что `@shagi/i18n` сам не зависит ни от
  чего продуктового (`core`/`app`/...) — зависимость однонаправленная.
