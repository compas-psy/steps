# ADR-0005. SQLite-биндинг: порт драйвера, `node:sqlite` для тестов/CI, `@tauri-apps/plugin-sql` для приложений

- Статус: принято
- Дата: 2026-08-31
- Автор: владелец требований (через агента, пакет работ E02.1)
- Отклонение от: не отклонение, а конкретизация `docs/spec/SPEC/00_MASTER_IMPLEMENTATION_TZ.md`
  §2 («Native: SQLite, WAL; foreign keys ON; migrations; FTS5») — ТЗ фиксирует
  требования к самой базе, но не называет, через что именно JavaScript
  получает к ней доступ внутри Tauri.

## Контекст

ТЗ (`00§2`) требует на нативе SQLite с WAL, включёнными внешними ключами,
миграциями и FTS5; и одновременно фиксирует Tauri 2 как shell для native
(`00§1`, `00§2` «Client/toolchain»). Это ставит конкретный вопрос, на который
ТЗ не отвечает: **приложение работает в Tauri, то есть весь JavaScript
(`packages/app`, `packages/storage`) выполняется в webview браузерного
движка ОС, а не в процессе Node.js.** Продакшен-сборка Tauri не встраивает
Node.js рантайм вообще — есть Rust-бинарник и webview, и ничего третьего.
Отсюда прямое следствие: **`node:sqlite` физически не может работать внутри
собранного приложения**, каким бы удобным он ни был, — там нет `node:`
модулей, потому что нет Node.

Одновременно этот пакет работ обязан прогоняться в контейнере, где нет ни
Android SDK, ни системных библиотек/рантайма Tauri (упомянуто в задании
явно) — то есть вариант «просто гонять тесты через настоящий Tauri» здесь
недоступен физически, а не по выбору.

Рассмотренные варианты получения доступа к SQLite из TypeScript-кода
`packages/storage`:

1. **`node:sqlite`** — модуль, встроенный в Node.js начиная с 22.5 (стабильный
   как экспериментальный флаг), доступен без флага в Node 24.20.0 (наша
   зафиксированная версия, ADR-0001). Синхронный API поверх `libsqlite3`.
   Работает **только там, где есть процесс Node.js** — это `pnpm test`,
   `pnpm typecheck`, CI. Внутри собранного Tauri-приложения такого процесса
   нет.
2. **`better-sqlite3`** — популярный нативный addon (N-API) с похожим
   синхронным API. Тоже требует процесс Node.js (плюс компиляцию
   platform-specific `.node`-бинарника под каждую ОС/архитектуру — Android
   ABI в их числе не первоклассная цель) — та же проблема, что и у
   `node:sqlite`, просто с дополнительной болью сборки, без выигрыша.
3. **`@tauri-apps/plugin-sql`** — официальный плагин экосистемы Tauri
   (`tauri-apps` organization), оборачивает `sqlx` на Rust-стороне. Frontend
   вызывает `Database.load('sqlite:app.db')` и SQL-методы через Tauri IPC
   (`invoke`); файл БД живёт в app-private директории, которую сам Tauri уже
   даёт (та же директория, что нужна для вложений, `01§24`). Работает
   **только внутри настоящего Tauri-рантайма** (desktop и Android shells) —
   не запускается в этом контейнере и не запускается в `vitest` напрямую.
4. **SQLite в WASM (`sql.js`/`wa-sqlite`)** — SQLite, скомпилированный в
   WebAssembly, исполняется прямо в webview/браузере, БД живёт в памяти или
   на OPFS. Соблазнительно единым кодом закрыть и native, и test — но:
   - ТЗ явно фиксирует другую пару для web: «Web: IndexedDB через versioned
     repository adapter» (`00§2`) — WASM SQLite в вебе не заменяет это
     требование, а дублирует его вторым хранилищем без причины;
   - на native (внутри Tauri webview) WASM SQLite означал бы, что файл БД
     живёт в песочнице webview (OPFS/IndexedDB самого webview), а не как
     обычный файл ОС — то есть нет реального native-файла, который можно
     штатно бэкапить/открывать сторонними инструментами/держать рядом с
     вложениями в одной app-private директории (`01§24`);
   - производительность на больших датасетах (перф-бюджеты `00§12`: search
     100k задач p95 <250мс) для WASM SQLite обычно ниже нативного
     `sqlx`/`libsqlite3` из-за прослойки WASM и однопоточной модели без
     mmap-WAL в большинстве сборок.

   Вывод: WASM SQLite не решает задачу лучше, чем уже предписанная ТЗ пара
   (SQLite нативно / IndexedDB в вебе), а вводит третье хранилище без
   выигрыша ни для одной из существующих двух платформ.

## Решение

**Порт драйвера, а не прямая зависимость.** `packages/storage/src/sqlite/driver-port.ts`
объявляет `SqliteDriverPort` — асинхронный интерфейс (`execute`/`queryAll`/
`queryOne`/`transaction`/`close`) поверх параметризованных SQL-запросов.
Ни один код в `packages/storage`, кроме будущего SQLite-адаптера (следующий
пакет работ), не знает о конкретном биндинге — только об этом порту.

**Две реализации порта**, обе — задача следующего пакета работ (сам
SQLite-адаптер здесь не пишется, см. задание E02.1 «Границы»):

| Реализация               | Где работает                                   | Роль                                                                                |
| ------------------------ | ---------------------------------------------- | ----------------------------------------------------------------------------------- |
| `node:sqlite`            | `pnpm test`/`pnpm typecheck`/CI (процесс Node) | Тесты контракта хранилища, integration-тесты командного слоя без Tauri              |
| `@tauri-apps/plugin-sql` | Desktop/Android Tauri shells (webview + Rust)  | Настоящие приложения — единственный путь, физически работающий в собранном продукте |

Это прямо то направление, которое было предложено в задании пакета работ, и
оно проверено, а не принято на веру:

- **Feasibility `node:sqlite` в этом контейнере проверена эмпирически**
  (Node 24.20.0, зафиксированный ADR-0001): `DatabaseSync` из `node:sqlite`
  создаёт файловую БД, `PRAGMA journal_mode=WAL` реально переключает режим
  на файловой БД (`journal_mode: 'wal'`; для `:memory:` SQLite сам всегда
  остаётся на `'memory'` — это ограничение SQLite, не `node:sqlite`, и не
  мешает: тесты контракта используют либо временный файл, либо не зависят
  от WAL напрямую), `PRAGMA foreign_keys=ON` включается и подтверждается
  `PRAGMA foreign_keys` → `1`, `CREATE VIRTUAL TABLE ... USING fts5(...)`
  выполняется без ошибки, `sqlite_version()` → `3.53.4`. Все четыре
  требуемых `00§2` свойства (WAL, foreign keys, миграции — это уже наш
  собственный механизм из `../migration/`, FTS5) достижимы через
  `node:sqlite` без единой внешней зависимости — он встроен в Node 24, не
  требует `pnpm add`.
- **`@tauri-apps/plugin-sql` — по построению официального пакета Tauri**:
  публикуется той же организацией, что и сам Tauri 2 (`00§2`), поддерживает
  SQLite через `sqlx`, работает по IPC из webview, что и объясняет форму
  `SqliteDriverPort` (все методы асинхронны, `transaction` — замыкание, а не
  голые `BEGIN`/`COMMIT` — под IPC два раздельных вызова физически не
  гарантируют, что между ними не проскочит третий, если вызывающий код не
  дисциплинирован; замыкание снимает этот риск конструктивно). Включение
  FTS5 в конкретной версии `sqlx`/`libsqlite3-sys`, которую подтянет плагин,
  и точная настройка WAL/foreign keys на его стороне — **предмет проверки
  следующего пакета работ** (SQLite-адаптер): в этом контейнере нет Rust
  тулчейна Tauri, чтобы прогнать `cargo build` и подтвердить cargo-фичи
  эмпирически, как это сделано выше для `node:sqlite`. Это не блокер
  решения — сам факт, что плагин официальный и специально существует для
  ровно этой задачи (SQL из Tauri webview), достаточен для выбора его как
  направления; конкретную настройку feature-флагов фиксирует ADR или
  комментарий уже в реализации следующего пакета, если понадобится
  отклонение.

**Почему это не «третья реализация вместо двух», а именно «две реализации
одного порта»:** обе стороны реализуют один и тот же `SqliteDriverPort`, а
не два разных публичных API. Код, который строится поверх порта (будущий
SQLite-адаптер репозиториев, `../ports/*`), пишется один раз и работает с
обеими реализациями без изменений — расхождение между "как ведёт себя SQLite
в тестах" и "как он ведёт себя в реальном приложении" становится
невозможным по конструкции, а не по дисциплине.

## Последствия

**Плюсы**

- Тесты контракта хранилища (`../contract/storage-contract.ts`) в будущем
  SQLite-адаптере смогут гонять реальный SQLite (не мок, не WASM-эмуляцию) в
  каждом `pnpm test`/PR CI без Android SDK, без Rust-тулчейна, без сети —
  `node:sqlite` уже есть в зафиксированном Node 24.20.0.
- Единственная точка правды о том, «что значит уметь говорить с SQLite» —
  `SqliteDriverPort` — линия, вдоль которой в следующем пакете работ и
  пишется весь SQL/схема/индексы/FTS5, использующие уже готовые
  `../schema/*` и `../migration/*` из этого пакета работ.
- `@tauri-apps/plugin-sql` даёт файл БД в app-private директории ОС — тот же
  дом, что и у вложений (`01§24`) — а не песочницу webview, что важно для
  бэкапа/восстановления (`02§15`) штатными средствами ОС.

**Минусы и как они удержаны под контролем**

- Два биндинга — это два места, где может незаметно разойтись поведение
  SQLite (версия движка, включённые compile-time опции). Удержано тем, что
  оба обязаны проходить один и тот же `runStorageContract` (`../contract/`,
  этот же пакет работ) — расхождение в наблюдаемом поведении красным падает
  в тесте, а не всплывает в проде.
- Настройка `sqlx`/`libsqlite3-sys` под FTS5 на стороне `@tauri-apps/plugin-sql`
  не проверена эмпирически в этом пакете работ (нет Rust-тулчейна в
  контейнере) — явно вынесено в задачу следующего пакета работ (SQLite-
  адаптер), а не молчаливо предположено. Если потребуется отклонение
  (например, cargo-фича, которую нужно включить явно) — это будет отдельный
  ADR или задокументированный шаг в реализации адаптера.
- `node:sqlite` официально маркирован Node.js как experimental (предупреждение
  `ExperimentalWarning` при первом импорте, подтверждено в этом же прогоне).
  Риск снят тем, что он используется **только** в тестовом/CI-контуре, не в
  продакшен-сборке приложения — там его вовсе нет физически (см. «Контекст»),
  так что нестабильность API между минорными версиями Node касается только
  тестового инструментария, а не выпускаемого продукта.

## Дополнение от 2026-09-02: `@tauri-apps/plugin-sql` отвергнут, мост свой

Решение выше оставляло за следующим пакетом работ проверку плагина —
дословно: «Включение FTS5 … и точная настройка WAL/foreign keys на его
стороне — предмет проверки следующего пакета работ … в этом контейнере нет
Rust тулчейна». Проверка сделана. Тулчейн появился, плагин прочитан,
и **направление не подтвердилось**.

### Что выяснилось

`tauri-plugin-sql` 2.4.1, исходники в `~/.cargo/registry`:

1. **Команды транзакции нет вовсе.** Плагин выставляет ровно четыре:
   `load`, `close`, `execute`, `select` (`src/commands.rs`).
2. **Соединение открывается пулом.** `DbPool::connect` →
   `Pool::connect(conn_url)` (`src/wrapper.rs:91`), а у `sqlx`
   значение по умолчанию — `max_connections: 10`
   (`sqlx-core/src/pool/options.rs:151`).

Из второго следует главное: `BEGIN` и `COMMIT`, отправленные двумя
отдельными `execute`, могут уехать на РАЗНЫЕ соединения пула. Транзакция
через этот плагин невыразима не «при неаккуратном использовании», а
структурно.

Для ШАГОВ это дисквалификация, а не неудобство. Весь write-путь построен
на том, что сущность и её outbox-запись ложатся одной транзакцией (`00§7`,
`ports/transaction.ts`), а общий контракт хранилища
(`contract/storage-contract.ts`) проверяет откат чтением базы после
форсированного сбоя. Хранилище, где транзакция — фикция, этот контракт не
проходит.

### Что вместо

Собственный узкий мост в оболочке: `apps/mobile/src-tauri/src/sqlite.rs` —
**одно** соединение `rusqlite` под мьютексом и команды
`sqlite_open`/`execute`/`query`/`snapshot`/`restore`/`close`. Схема, SQL и
транзакционный протокол остаются в `@shagi/storage`
(`sqlite/native-bridge.ts`): в оболочке нет ни одного SQL-оператора и ни
одного имени таблицы — правило «в `apps/*` нет бизнес-логики» (SPEC/00 §3)
распространяется и на схему.

Порт драйвера (`SqliteDriverPort`) и обязательство «обе реализации проходят
один и тот же `runStorageContract`» — сохранены дословно и исполнены:
`test/sqlite/native-bridge-contract.test.ts` гоняет весь общий контракт
через мост, причём каждое значение на границе проходит
`JSON.parse(JSON.stringify(...))` — там, где настоящий IPC теряет точность
64-битных целых.

`rusqlite` берётся с фичей `bundled`: движок SQLite компилируется в
бинарник приложения, системный не используется. FTS5 в такой сборке
включён — проверено не по памяти, а по коду
`libsqlite3-sys-0.38.2/build.rs:159` (`-DSQLITE_ENABLE_FTS5`) и рантайм-тестом
(`sqlite_compileoption_used('ENABLE_FTS5')` плюс реальный `MATCH`-запрос).

Три обязательных свойства `00§2` (WAL, внешние ключи, FTS5) проверяются при
КАЖДОМ открытии базы, и несоответствие любого — исключение с диагностикой:
`BridgedSqliteDriver.open`. Молчаливого отката на IndexedDB нет ни на одном
пути; `resolveStorageBackend('sqlite')` бросает исключение с прямым
указанием, что это ошибка сборки оболочки.

### Совместимость с уже установленными сборками

Установки на IndexedDB (ADR-0006) существуют. Принято **первое** из двух
предложенных владельцем решений: одноразовый перенос при первом запуске
версии с нативной SQLite (`@shagi/app` `state/backend-migration.ts`).

Переносится ВСЁ состояние устройства, а не «данные человека»:
`dumpForMigration`/`loadFromMigrationDump` включают tombstone, очередь
синхронизации, конфликты и партии импорта. Потерять tombstone значит
воскресить удалённое при первой же синхронизации; потерять outbox — не
отправить изменения, которые человек уже сделал.

После успешного переноса база IndexedDB **удаляется**, и это не уборка.
Без удаления возникает дыра: человек стирает локальные данные (M52,
`05§13`), SQLite пустеет, и следующий запуск снова видит непустой источник
— стёртые задачи воскресают. Метка в настройках — вторая линия на случай,
если удаление не удалось.

### Что осталось незакрытым

Мост живёт в `apps/mobile`. Оболочка Windows (Tauri, будущая волна) получит
ту же нужду; тогда его место — общий плагин Tauri или общий крейт, а не
копия. Отмечено здесь, чтобы копия не появилась молча.
