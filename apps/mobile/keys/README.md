# Отладочный ключ подписи Android

## Главное, одной строкой

**Debug-APK — артефакт разработки. Производственной сборкой он не является
никогда и по тегу `shagi-v*` не публикуется: GitHub Release создаётся только
для release-сборки, подписанной боевым ключом и прошедшей проверку готового
файла (`.ultraplan/research/04-android-release.md` §3).**

Для производственной подписи достаточно полного комплекта четырёх секретов —
`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`,
`ANDROID_KEY_PASSWORD` — и заполненного `apps/mobile/EXPECTED_SIGNER.txt`.
Никакого дополнительного секрета подписи не требуется. Неполный комплект — не
повод собрать debug: сборка падает, потому что половина настройки это ошибка,
а не выбор (`apps/mobile/scripts/android-release-gate.mjs` → `signingPolicy`).

## Зачем он лежит в репозитории

Без секретов подписи (`ANDROID_KEYSTORE_BASE64` и соседних) сборка выпускает
**debug-APK**, а его подписывает отладочный ключ Android-плагина. Этот ключ
плагин генерирует случайным **на той машине, где собирает**. Каждый прогон
GitHub Actions — новая чистая виртуалка, то есть новый ключ и новая подпись.

Последствие ровно одно, зато злое (инцидент разобран у соседнего продукта,
`compas-psy/zapiski`, — см. `.ultraplan/research/04-android-release.md`):
первая сборка ставится, а каждая следующая отказывается. Android не даёт
установить пакет с тем же `applicationId`, но чужой подписью, и показывает
«Приложение не установлено» — без объяснения причины.

`debug.keystore.base64` делает подпись debug-сборок **постоянной**: любая
следующая ставится поверх предыдущей, как и должно быть.

## Почему это не утечка

Ключ отладочный и ничего не защищает:

* пароль и алиас — общеизвестные значения Android (`android`,
  `androiddebugkey`), точно такие же лежат в `~/.android/debug.keystore` у
  каждого, кто хоть раз собирал Android-проект;
* в Google Play и RuStore подписанное им приложение не принимается;
* обновлением поверх релизной сборки такой APK не встанет — у релиза другой
  ключ, и это правильно;
* владение им не даёт доступа ни к чьим данным: у ШАГОВ в R1 нет сервера, нет
  аккаунта, все данные — на устройстве самого человека.

**Боевой ключ здесь не лежит и лежать не может.** Он живёт только в секретах
репозитория; как только они появятся, production-сборка перестанет
пользоваться этим файлом сама — см. шаг «Подготовить keystore» в
`.github/workflows/build-android.yml`.

## Чего постоянный отладочный ключ НЕ решает

Он решает ровно одно: debug-сборка ставится поверх предыдущей debug-сборки.

Он **не** делает пакет производственным. Для проверки Play Защиты
`CN=Android Debug` — первый признак того, что приложение собрано не для
людей, и разбор в `apps/mobile/scripts/android-release-gate.mjs` →
`verifySigner` отвергает такой сертификат жёстко, а не предупреждением.
Именно поэтому дорога «нет секретов → отладочный ключ → GitHub Release»
из сборки исключена целиком: правило — в шапке
`.github/workflows/build-android.yml`, логика — в
`apps/mobile/scripts/android-release-gate.mjs`, испытывается —
`apps/mobile/test/android-release-gate.test.ts`.

## Как заменить

```sh
keytool -genkeypair -v -keystore debug.keystore \
  -storepass android -alias androiddebugkey -keypass android \
  -keyalg RSA -keysize 2048 -validity 10950 \
  -dname "CN=SHAGI Debug, OU=Development, O=SIMPAS, L=Moscow, C=RU"
base64 -w 100 debug.keystore > debug.keystore.base64
rm debug.keystore
```

После замены все, у кого стоит debug-сборка, должны будут удалить приложение и
поставить заново — подпись сменится. Поэтому менять его без нужды не стоит.

## Почему коммитится обычным `git add`, а не исключением в `.gitignore`

`*.keystore` в корневом `.gitignore` игнорирует именно `debug.keystore` —
файл, который создаёт команда выше и который здесь никогда не остаётся (его
удаляют сразу после кодирования в base64, как в примере выше). В репозитории
живёт только `debug.keystore.base64` — под шаблоны секретных форматов
(`*.jks`, `*.keystore`, `*.p12`, `*.pem`) он не подпадает, поэтому `git add`
подхватывает его как обычный текстовый файл, без исключений в `.gitignore`.
Заводить исключение здесь не нужно и не следует: `scripts/check-signing-secrets.mjs`
специально падает на любом `!…` для секретных форматов (см. комментарий в
`.gitignore`) — это тот самый сторож, из-за которого у Записок чуть не уехал
в git настоящий релизный ключ.
