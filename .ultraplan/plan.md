## Раскладка монорепозитория
Строго по `SPEC/00_MASTER_IMPLEMENTATION_TZ.md §3`, с одним добавлением
(`packages/i18n`, оформляется ADR-0004):

```
apps/{web,desktop,mobile}          — только оболочки, ни одного экрана
packages/contracts                 — DTO / Zod / типы под OpenAPI
packages/core                      — домен: сущности, команды, инварианты, время, повторы, rank
packages/storage                   — репозитории + адаптеры SQLite / IndexedDB
packages/sync                      — outbox, HLC, merge (в волне 1 — только форма данных)
packages/nlp                       — детерминированный русский парсер
packages/importer                  — Todoist / CSV / backup
packages/ui                        — токены и компоненты, без продуктовых строк
packages/app                       — ВСЕ экраны, маршруты, поведение
packages/i18n                      — каталоги строк, ICU, проверка полноты
packages/telemetry                 — только санированные контракты событий
packages/platform                  — интерфейсы возможностей платформы
server/, deploy/                   — каркас под волну 2
```

**Инвариант:** ни одного экрана, бизнес-правила, правила NLP/sync и ни одной
пользовательской строки в `apps/*`.

## Что закладывается с первого коммита, иначе переписывать
Из отчётов разведки — семь швов, которые поздняя вставка сломает:

1. **Единая точка входа `CreateTaskCommand`** — через неё идут Quick Add,
   импорт и все будущие адаптеры. Прямая запись в БД запрещена.
2. **Один domain-валидатор на 38 правил** — общий для локальных команд,
   входящих sync-патчей, натива и веба.
3. **Детерминированный UUIDv5** для occurrence / subtask / checklist повторов
   плюс remove-wins граница `stop_after_occurrence_seq`.
4. **Outbox пишется в той же локальной транзакции**, что и сущность.
5. **Per-field HLC и `revision`** на изменяемых сущностях.
6. **Tombstone вместо жёсткого удаления**, retention 90 дней.
7. **`capture_state`, `source`/provenance, snapshot имени проекта** на Task.

## Метод
Разработка по `superpowers`: TDD RED-GREEN-REFACTOR, самодостаточные задачи
субагентам, проверка перед объявлением готовности. Всё, что касается
интерфейса, — через `impeccable`. После каждого эпика: моя валидация, коммит,
пуш, короткий отчёт владельцу.

## Риски
- **~70% экранов матрицы не нарисованы** (16 из 52 мобильных, 6 из 20
  десктопных, ST01–ST21 — ни одного). Проектируются по токенам; нормативна
  матрица `12_SCREEN_STATE_MATRIX.md`, а не картинка.
- **DS-бандл — слепок чужого продукта** (ПРАКТИКА). Токены совпадают 1:1,
  компонентный API нет. Задачные компоненты пишутся с нуля.
- **Шрифтов Geist нет в поставке**, а поставленный `fonts.css` тянет Google
  Fonts, что ТЗ прямо запрещает. Вендорим `.woff2` из пакета Vercel (SIL OFL).
- **Перф-бюджеты — релизные гейты без определённого стенда.** Android
  «mid-range» замораживается конкретной моделью в ADR-0003.
- **Подпись Android — точка невозврата.** Схема заимствуется у Записок
  целиком, fail-closed (`.ultraplan/research/04-android-release.md`).
- **Веб обязан повторить семантику ранжирования FTS5** один-в-один. Пишется
  дважды, проверяется общими golden-тестами.

### E06 — закрыт (Today: выборки, группы, precedence, виртуализация)
`selectTodayTasks` (`packages/core/src/rules/select-today-tasks.ts`) —
объединение трёх индексных запросов, дедупликация по `id` до
классификации (структурно исключает повтор задачи в двух группах, не
проверяется постфактум), группировка через уже принятую
`classifyTaskForToday` (не переопределена). Экран `Today`
(`packages/app/src/screens/Today.tsx`) — весь прецедент `01§6` (все шесть
пунктов) и матрица M06–M11: Empty/Normal, Complete/Reschedule/Change
deadline, сворачиваемые группы (M08 — решение пакета работ: не вводить
библиотеку виртуализации на 20-50 строках, это преждевременно на этом
масштабе; настоящая виртуализация больших датасетов — будущий эпик E21),
назначение «Главное» (прямое/с подтверждением переноса даты/замена одной
из трёх при переполнении), мультивыбор + bulk Today/Tomorrow строго для
группы «Не по плану» (структурно ограничено — остальные пять групп не
получают проп мультивыбора вовсе, не просто скрывают его условием).
`ScreenId 'todayEmpty'` (задел E04.1) переиспользован как согласованное
имя.

Четыре последовательных пакета работ (E06.1–E06.4) на одном файле — не
параллелились намеренно, чтобы не ловить конфликты правок одного и того
же экрана. На каждом лично воспроизведена своя адверсариальная проверка:
дедупликация кандидатов (Map → конкатенация, тест поймал дубликат);
отсутствие перезапроса `selectTodayTasks` после успешной команды (список
не обновлялся, тест поймал); отключённая проверка лимита Focus (4-я
задача патчилась напрямую вместо диалога замены, тест поймал); отсутствие
`refreshGroups()` после bulk-действия (перенесённые задачи оставались в
старой группе, тест поймал). Каждая — сломано → тест упал на нужном месте

### E11 — частично (движок повторов, командный слой; UI не начат)

Схему E01 заложила заранее целиком (`RecurrenceSeries` со всеми полями,
включая `stopAfterOccurrenceSeq`/`templateRevision`; `seriesId`/
`occurrenceSeq`/`generatedFromOccurrenceId` на Task; детерминированные
`deriveOccurrenceId`/`deriveSubtaskId`/`deriveChecklistItemId` через
UUIDv5) именно затем, чтобы этому эпику не понадобилась миграция на
боевых базах — комментарий `entities/recurrence-series.ts` прямо
говорит: «движок повторов это эпик E11 и здесь не реализуется». Этот
пакет работ реализует ровно этот движок:

- якорная арифметика (`temporal/recurrence-anchor.ts`) — scheduled
  (первый слот СТРОГО после даты завершения/пропуска, просрочка не
  плодит пачку прошлых копий) для дня/недели/месяца (число 31
  буквально пропускает короткие месяцы, не constrain)/года (29
  февраля только в високосные); completion (дата завершения +
  интервал, `overflow:'constrain'`);
- `completeOccurrenceCommand`/`skipOccurrenceCommand` — переиспользуют
  `completeTaskCommand` (тот специально держал этот шов с E01: «не
  генерирует следующий occurrence — задача будущего пакета работ»),
  генерируют следующий occurrence детерминированным id, копируют
  subtasks/checklist текущего неполными, переносят относительные
  дедлайн/available-from смещением в днях; локально уважают
  `stopAfterOccurrenceSeq` (свою половину remove-wins границы §11.8 —
  сравнение с входящим sync-патчем "regardless of HLC ordering"
  остаётся нереализованной заглушкой, sync физически не существует);
- `undoCompleteOccurrenceCommand` — откатывает завершение/пропуск,
  убирает сгенерированный next occurrence, если он НЕТРОНУТ с момента
  генерации (`revision===1n`), откатывает `nextOccurrenceSeq` серии
  так, что повторная генерация даёт тот же детерминированный id;
- `updateSeriesTemplateCommand` ("Вся серия") / обычный
  `updateTaskCommand` ("Это повторение", новой команды не потребовалось);
- `deleteSeriesCommand` — выставляет `stopAfterOccurrenceSeq`/
  `active:false` И tombstone-ит текущий активный occurrence (решение
  пакета работ: «удалить всю серию» читается как продуктовый эквивалент
  обычного удаления для recurring-задачи).

Сознательно вне объёма: §11.8.1 (сходимость `template_revision` между
устройствами — сценарий физически не возникает на одном устройстве),
§11.9 ветка "другое устройство уже изменило", §11.10/§11.11 (restore
из истории завершённых — экран «Завершённые», M36, принадлежит E12,
ещё не начатому).

Личная adversarial-проверка после сдачи: убрал сравнение с
`stopAfterOccurrenceSeq` из условия остановки генерации — тест
