# Заимствование: подпись Android и релизный контур

Источник: `compas-psy/zapiski` @ `4257fdb` — соседний продукт СИМПАС на том же
стеке (pnpm-монорепо, Tauri 2 Mobile, тот же расклад `apps/` + `packages/` +
`server/`). Схема боевая: комментарии в файлах разбирают реальные инциденты,
а не описывают намерения.

Файлы-образцы:
- `scripts/make-android-keystore.sh`
- `.github/workflows/build-android.yml` (1371 строка)
- `apps/mobile/scripts/android-release-gate.mjs` — вся политика в одном
  тестируемом модуле, `apps/mobile/test/android-release-gate.test.ts`
- `apps/mobile/android-permissions.txt`, `apps/mobile/EXPECTED_SIGNER.txt`
- `apps/mobile/keys/debug.keystore.base64` + `keys/README.md`
- `docs/dev/build-and-release.md` (раздел RuStore), `docs/dev/contributing.md`

## 1. Правило имён СИМПАС — одно на все продукты системы

```
Имя файла:         simpas-<продукт>-<версия>.apk
Тег релиза:        <продукт>-v<версия>
Постоянная ссылка: /updates/latest/<продукт>.apk
```

`<продукт>` — сейчас `praktika | zapiski | momenty`; ШАГИ расширяют набор
значением `shagi`. Приставка `simpas` — по имени СИСТЕМЫ, а не одного продукта:
имя одного продукта на файлах остальных закрепляет путаницу, из-за которой
КОМПАС транслитерируется тремя способами сразу (`kompas`, `compas`, `cmpas`).

Ни хеша коммита, ни номера прогона в имени: человек видит его в загрузках, и
`-a3f9c21` ему ничего не сообщает. Релиз соответствует ВЕРСИИ, а не прогону —
пересобрали ту же версию, обновили существующий релиз.

Правило касается **имён артефактов**. `applicationId` (`ru.cmpas.<продукт>` →
для нас `ru.cmpas.shagi`), ключ подписи, домен `cmpas.ru` и организация
`compas-psy` не переименовываются: смена `applicationId` означает для системы
ДРУГОЕ приложение — обновление поверх установленного перестаёт работать, у
человека оказываются две иконки.

Источник истины по версии — `apps/mobile/src-tauri/tauri.conf.json`. Тег,
не совпавший с версией, роняет сборку до компиляции.

## 2. Ключ подписи

Создаётся **владельцем вручную, один раз на всю жизнь продукта**, скриптом
`scripts/make-android-keystore.sh`: RSA 4096, срок 30 лет (`10950` дней),
путь по умолчанию вне репозитория, отказ при попытке положить ключ в рабочее
дерево. Скрипт ничего не отправляет — печатает base64 и отпечаток.

Четыре секрета в GitHub Actions:
`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`,
`ANDROID_KEY_PASSWORD`.

Ключ невосстановим: потеря = невозможность выпускать обновления навсегда.
Смена ключа = новая личность приложения, у всех установивших обновление
перестаёт вставать.

## 3. Два канала, которые не смешиваются

**production** — тег `<продукт>-v*`, пуш в ветку по умолчанию, ручной запуск с
явно выбранным каналом. APK либо собран как release, подписан постоянным
ключом и прошёл проверку готового файла, либо его нет вовсе. Нет хотя бы
одного из четырёх секретов — падаем ДО получаса компиляции.

**development** — pull request, чужая ветка, ручной запуск без выбора.
Допустим debug-APK, честно named `-debug`. Живёт семь дней во вкладке
Actions и не попадает ни в постоянную ссылку, ни в фид обновлений, ни в
GitHub Release, ни в кнопку «Скачать».

Неполный комплект секретов роняет сборку **на любом канале**: половина
настройки — это ошибка, а не повод собрать что-нибудь.

## 4. Почему это переписывалось — инцидент, который нельзя повторить

Заказчик: «сертификат подписи в андроид блокируется проверкой при установке и
не проходит проверку Play Защиты». Дело было не в ключе. Сборка работала
**fail-open**: нет секретов → молча берём отладочный ключ, собираем `--debug`,
и дальше те же строки кладут результат в публичную ссылку. То есть кнопка
«Скачать» могла отдавать пакет с `CN=Android Debug` — первое, на что реагирует
Play Защита.

Единственная дорога наружу после переписывания:

```
ANDROID_* → проверка keystore и алиаса → EXPECTED_SIGNER_SHA256 →
release-сборка → zipalign → apksigner sign (v1+v2+v3) → apksigner verify →
отказ при CN=Android Debug → отпечаток APK совпал с ключом →
verified_release=true → сервер, Release, фид обновлений
```

## 5. Что именно проверяется

- **До сборки:** keystore восстанавливается из base64 и непуст; алиас
  найден; пароль хранилища подходит; пароль ключа подходит (через `-certreq`,
  который требует приватный ключ и ничего не меняет в хранилище).
- **Отпечаток из keystore** становится `EXPECTED_SIGNER_SHA256` — точкой
  отсчёта. Публичный отпечаток печатается в лог сознательно: по нему сверяют,
  что выпуск подписан тем же ключом, что и прошлый.
- **Сверка с репозиторием:** `apps/mobile/EXPECTED_SIGNER.txt` обязан совпасть
  с отпечатком keystore. Расхождение — отказ сборки, а не предупреждение:
  иначе App Links (`assetlinks.json`) ломаются МОЛЧА — сборка зелёная, APK
  ставится, а вход по ссылке из письма уводит в браузер.
- **После подписи:** `apksigner verify --print-certs` по ГОТОВОМУ файлу,
  отказ при `CN=Android Debug`, отпечаток APK сверяется с ожидаемым. «Keystore
  восстановился» и «APK подписан этим ключом» — разные утверждения.
- **Разрешения готового пакета:** `aapt2 dump permissions` по собранному APK
  сверяется с `android-permissions.txt`. Шаблон манифеста и итоговый пакет —
  разные вещи: разрешение может приехать из зависимости, которую никто не звал.
  Строка без объяснения не проходит проверку: разрешение без причины — это
  разрешение, которое никто не пересмотрит.
- **Паспорт сборки** (provenance JSON) едет рядом с APK: канал, версия,
  applicationId, SHA-256 пакета, отпечаток подписанта, тип сборки.

## 6. Подпись руками, а не конфигом Gradle

`zipalign -p -f 4`, затем `apksigner sign` со схемами **v1+v2+v3** явно:
v2 обязательна (без неё пакет проверяется только JAR-подписью), v3 даёт
возможность когда-нибудь сменить ключ без переустановки, v1 — совместимость
со старым софтом. v4 не нужна: она про инкрементальную установку с ADB.

Сгенерированный `build.gradle.kts` — чужой файл; править его патчем ради
подписи рискованнее, чем вызвать штатные инструменты. Заодно `verify
--print-certs` даёт доказательство стабильности подписи прямо в логе.

## 7. Постоянный debug-ключ в репозитории

`apps/mobile/keys/debug.keystore.base64` — общеизвестный отладочный ключ
(`android`/`androiddebugkey`), закоммичен сознательно. Свой ключ
Android-плагин генерирует на машине сборки, а раннер GitHub каждый раз новый:
новый ключ → новая подпись → первый APK встаёт, каждый следующий отказывается
с «Приложение не установлено» без объяснения причины. Ключ ничего не защищает
и в магазинах не принимается — почему это не утечка, объяснено в
`keys/README.md`.

## 8. R8 и нативный мост

Release собирается с `isMinifyEnabled = true`, а Rust зовёт Kotlin по
строковому имени класса через JNI. R8 такие вызовы не видит: переименует класс
и выкинет «неиспользуемые» методы — APK соберётся, установится и упадёт при
первом обращении к платформе. Правило кладётся файлом `proguard-*.pro`:

```
-keep class <applicationId>.** { *; }
-keepclasseswithmembernames class * { native <methods>; }
```

## 9. RuStore

Отдельного шага упаковки не требуется: RuStore принимает **тот же подписанный
релизный APK**, что и прямая раздача с сайта. Загрузка в консоль руками,
отдельного workflow под это нет.

Что важно перед первой загрузкой (по опыту Записок):

1. **Политика конфиденциальности должна быть настоящей.** RuStore требует
   рабочую ссылку при публикации; это реквизиты юрлица/ИП, их не восстановить
   из кода. У Записок она до сих пор помечена «ЧЕРНОВИК, не публиковать без
   юридической проверки» с плейсхолдерами `{{ФИО ОПЕРАТОРА}}`.
2. **Зависимости от Google Play Services быть не должно.** У Записок
   единственный след — `AD_ID` и `BIND_GET_INSTALL_REFERRER_SERVICE`,
   транзитивно из AppMetrica; на устройстве без GMS не блокируют запуск.
   Для ШАГОВ, где аналитика по ТЗ opt-in и выключена по умолчанию, этих
   разрешений быть не должно вовсе.
3. **Свой апдейтер и апдейтер магазина — два независимых канала.** Конфликта
   нет (оба ведут на ту же версию), но при желании держать канал единым свой
   апдейтер отключается по источнику установки
   (`PackageManager.getInstallSourceInfo`).
4. **Материалы карточки.** Иконка есть (у нас — `assets/brand/`), скриншотов и
   графики в репозитории нет; собираются вручную под требования консоли на
   момент публикации — они меняются чаще, чем стоит фиксировать числом.

## 10. Соседние продукты как ориентир по разрешениям

Из `android-permissions.txt` Записок: «Соседние продукты на том же телефоне
ставятся молча: МОМЕНТЫ просят только `INTERNET`, ПРАКТИКА — `RECORD_AUDIO`».

Отдельно: `REQUEST_INSTALL_PACKAGES` убрано 23.08.2026 — им приложение
объявляет себя установщиком других приложений, это признак, по которому
Play Protect ловит дропперы, и из-за него блокировалась КАЖДАЯ установка
Записок вторым окном «всё равно установить».

**Для ШАГОВ R1** (локальный офлайн-продукт, без аккаунта, без облака, без
голоса, аналитика opt-in и по умолчанию выключена) ожидаемый список короче
всех соседей. Кандидаты:

| Разрешение | Зачем | Когда |
|---|---|---|
| `POST_NOTIFICATIONS` | локальные напоминания, Android 13+ | R1a |
| `SCHEDULE_EXACT_ALARM` / `USE_EXACT_ALARM` | точное время напоминания | R1a, по политике стора |
| `RECEIVE_BOOT_COMPLETED` | пересоздание расписания уведомлений после перезагрузки | R1a |
| `VIBRATE` | хэптика | R1b |
| `INTERNET` | **не нужен в R1a** — облака нет | R1b, вместе с аккаунтом |

Каждая строка — с объяснением, иначе проверка не проходит. `INTERNET`
добавляется только когда появляется то, что в него ходит: приложение без
сетевого разрешения — сильное и проверяемое утверждение о приватности
локального режима.
