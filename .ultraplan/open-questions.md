## A. Модель данных и домен

| # | Вопрос | Рекомендация |
|---|---|---|
| ?1 | Формат `owner_scope`. `02 §2` говорит только «local profile or account scope» | UUIDv7 локального профиля, создаётся при первом запуске. При входе в аккаунт значение **не меняется**, а к нему привязывается `account_id` — иначе слияние local→cloud потребует переписать каждую строку |
| ?2 | Алгоритм fractional rank и порог ренормализации. `02 §5` описывает поведение, но не алфавит и не число | LexoRank-подобные строки в base62, порог ренормализации — длина 64 символа, ренормализация транзакционная и пакетная |
| ?3 | Стартовое значение `occurrence_seq` и точка инкремента | Старт `1`; инкремент в той же локальной транзакции, что и завершение текущего occurrence. Ноль зарезервировать нельзя: он попадёт в UUIDv5 и «нулевой» occurrence станет неотличим от отсутствующего |
| ?4 | Обнуление `focus_date` на новый день. `01 §6`: «полночь не переносит вчерашний Focus вперёд», но не сказано, чистится ли поле | Не чистить. Никаких полуночных job — «Главное» выбирается условием `focus_date = today`, вчерашнее значение просто перестаёт совпадать. Фоновая задача-чистильщик породила бы sync-мутации на пустом месте |
| ?5 | Что делать, если правка `available_from` сдвигает её позже уже сохранённого `planned_date` | Отклонять правку `available_from` с внятным сообщением, а не двигать `planned_date` молча. Авто-сдвиг плана — изменение намерения пользователя без спроса |
| ?6 | Конкурентная генерация occurrence с одинаковым `occurrence_seq`, но разной вычисленной датой (completion-anchor, два устройства офлайн) | Считать `planned_date` обычным скалярным полем: per-field LWW по HLC. ID совпадает (UUIDv5), дубля нет; расхождение даты разрешается тем же путём, что любая конкурентная правка даты |
| ?7 | Материализовать ли R3-колонки (`source_channel`, `source_capture_batch_id`, `source_intent_id`) в миграциях волны 1 | Да, nullable, с первой миграции. `source` и так обязателен уже в R1. Добавить три nullable-колонки сейчас стоит ноль; добавить их потом — миграция на боевых базах |

## B. Продуктовое поведение

| # | Вопрос | Рекомендация |
|---|---|---|
| ?8 | Порядок очереди «Входящих» при действии «Пропустить» (`01 §2`) | FIFO по `created_at`; пропущенная карточка уходит в конец текущей сессии разбора и не возвращается, пока очередь не пройдена. Иначе «Пропустить» зациклится на одной задаче |
| ?9 | Семантика системного фильтра «Без даты» (`01 §16`) | `planned_date IS NULL` — фильтр про планирование. Задача с дедлайном, но без плана, обязана в нём быть: это ровно то, что человек ищет |
| ?10 | Перечень NLP service-токенов, по которым проверяется «остался ли читаемый заголовок» (`01 §1`) | Служебными считаются только токены, породившие принятый chip. Правило: если после их удаления не осталось ни одного символа кроме пробелов и пунктуации — сохранение блокируется |
| ?11 | Численный допуск clock skew для HLC (`02 §6`) | ±24 часа. Единственное число во всей документации — `06 §5` п.12 evil sync suite, «client clock skew ±24h». Тестовый сценарий, но брать другое значение неоткуда |

## D. Сборка, качество, релиз

| # | Вопрос | Рекомендация |
|---|---|---|
| ?17 | Чем и на чём мерить 13 перф-бюджетов. ТЗ даёт числа и называет их «assertions in CI/nightly», но не называет ни инструмента, ни стенда, ни методики p95 | Доменные и запросные бюджеты — Vitest bench на фиксированных датасетах (10k/100k задач, 500 карточек), p95 по 30 прогонам. Клиентские (запуск, keystroke) — Playwright trace. Android «mid-range» замораживается конкретной моделью в ADR: без названного устройства число не проверяемо |
| ?18 | Блокируют ли перф-тесты PR CI или только nightly | Только nightly и main. `08 §2` не включает perf в список шагов PR CI, а раннеры GitHub слишком шумные для p95 на PR |
| ?19 | Конкретные инструменты SAST / dependency-scan / secret-scan / license-scan — ТЗ называет шаги, но ни одного инструмента | osv-scanner (уязвимости), gitleaks (секреты), CycloneDX (SBOM), oxlint + `tsc --noEmit` как базовый статический анализ, license-checker по allowlist. Всё self-hosted-совместимо: `08 §3` требует переносимости между GitHub / GitVerse / self-hosted |
| ?20 | Формат redaction-тестов. `05 §6` называет их mandatory, но формата не задаёт | Логгер за фасадом, принимающим только типизированные поля; property-тест прогоняет корпус пользовательского контента через все точки логирования и падает при появлении подстроки в выводе |
| ?21 | Дополнять ли ручные корпуса генеративным фаззингом | Да, точечно: recurrence-движок и fractional rank — там комбинаторика, которую руками не перечислить. NLP оставить golden-корпусом (≥800 кейсов), как требует ТЗ |
| ?22 | Раннер и toolchain для сборок Android и Windows | Как у Записок: Android — `ubuntu-latest` + `android-actions/setup-android` + пин NDK; Windows — `windows-latest`. В этом контейнере Android SDK нет, поэтому мобильная сборка проверяется только в CI |
| ?23 | Шаблон и процесс ADR — ТЗ требует ADR, но ни шаблона, ни каталога не задаёт | `docs/adr/NNNN-краткое-имя.md`, формат Nygard (Контекст / Решение / Последствия), ADR в том же коммите, что и реализация |
